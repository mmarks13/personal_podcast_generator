Claude Opus 5, and why more effort made it worse

A near-frontier model at half the frontier's cost per task resets the math on anything agentic — the runs that loop for an hour and burn tokens the whole way. Alan: It wasn't the price. It's the effort dial, and it does something genuinely counterintuitive. Opus five has five effort settings — low, medium, high, xhigh, and max. The mental model everyone brings is a thermostat. Turn it up, get better answers.

Ada: More compute, more thinking, better output. That's the whole premise of the last two years.

Alan: Right. Except a developer named Cheng-Yuan Lee, who works on the FrontierCode benchmark, went and tested that, and found the dial isn't monotonic for coding. At higher effort, Opus five starts refactoring the code around a fix even when you only asked for the fix.

Ada: Define "starts refactoring."

Alan: His actual example is almost too clean. Given a task that needed a one-character change: at the lowest effort setting, Opus five changed exactly one character. At xhigh, it refactored the entire surrounding block of code.

Ada: And the benchmark counts that against it.

Alan: The benchmark counts every unsolicited change as an error. So on that task, more effort produced a lower score. You turned the dial up and the model got worse — not because it got dumber, but because it got busier.

Ada: Okay. That I can explain, and I think the explanation is the useful part. Anthropic's own framing of this model is that it's — their words — much stronger at verifying its work and iterating carefully until it succeeds. That's the headline capability.

Alan: Which sounds like an unalloyed good.

Ada: It sounds like an unalloyed good. But think about what "iterate until it succeeds" does to a one-line fix. There's nothing to iterate toward. The task was over after the first character. So the extra effort budget doesn't sit idle — it goes looking for things to improve. And on a small, well-scoped change, "things to improve" means "things to touch that you didn't ask me to touch."

Alan: The effort has to go somewhere.

Ada: The effort has to go somewhere. And Anthropic clearly knows this, because their migration guidance now tells developers to stop adding instructions like "include a final verification step" — because the model already does that, and telling it to do it again produces over-verification.

Alan: So the advice is: stop telling it to try harder.

Ada: Stop telling it to try harder. Which is a genuinely new shape of advice. For years the whole craft was coaxing more effort out of these things — think step by step, check your work, take your time. And here's a model where, for a certain class of task, that coaxing is actively counterproductive.

Alan: So how do I actually set the dial? Because this is a real decision I'd have to make Monday.

Ada: Say it as a rule.

Alan: The rule I'd take from this: match effort to how open-ended the task is, not to how much you care about it. Surgical edit, a bug in one function, a rename — cap it at high. Reserve xhigh and max for the genuinely sprawling work, the multi-file thing where you actually want it exploring. Using max on a small fix isn't buying quality, it's buying scope creep you then have to review back out.

Ada: And there's a hard edge to know about, too — a breaking change. If you were disabling the thinking step and cranking effort to xhigh or max, that combination now returns an error rather than running. So some existing setups will just stop working until someone reads the migration note.

Alan: Which people won't, and then they'll file a bug that isn't one.

Ada: As they do. But step back, because the design lesson is bigger than one model. We have spent this whole era treating capability as a single scale — more is better, full stop. This is a clean little counterexample. An eagerness that's a virtue on a hard problem is a defect on an easy one, and no single dial setting is right for both.

Alan: I'll admit a certain fellow-feeling for a system that, told to try harder, cannot stop tidying up things nobody asked it to.

Ada: I was going to let that go unsaid. The point for the listener, though: this is the first frontier release where the honest configuration advice is "less, sometimes." The price will get the headline. The dial is the part you'll actually feel.

The Stack v3: cleaning a hundred terabytes of code

Ada: Mine is the other end of the same pipe. Everyone watches the model. Almost nobody watches the data underneath it — and this week the data got a major release. The BigCode project, at Hugging Face, published The Stack, version three. It's the training corpus that open code models get built on.

Alan: The line that StarCoder came out of, a couple of years back.

Ada: The same lineage, exactly. And the scale first, because it's genuinely hard to picture. The full corpus, per the dataset card: one hundred and thirteen terabytes of source code. Seven hundred and seventy programming languages. Two hundred and twenty-four million repositories. Almost forty-four billion files.

Alan: That's not a dataset, that's a substantial fraction of the public code that exists.

Ada: It's a snapshot of GitHub, essentially, as of last August. But here's the number that tells the real story. The slice they package as ready-to-train is about sixteen terabytes. Roughly five trillion tokens.

Alan: So a hundred and thirteen terabytes goes in, and sixteen comes out the far end as usable.

Ada: And what happens in that gap is the entire craft. That's the part I want to walk, because "we cleaned it" is doing an enormous amount of work in that sentence.

Alan: Walk it.

Ada: Seven stages on the dataset card. First, they decode every file and detect what language it's actually in — using a tool called go-enry, because a file extension lies constantly. Then file-level license detection, with a scanner called ScanCode, so they know what each file is legally.

Alan: That second one matters more than it sounds. "Open source" isn't one license. Some of them let you train freely and some very much don't.

Ada: Which is exactly why it's a stage of its own. Then deduplication — and this is the big one. They use a technique called MinHash to find near-duplicate files. Not just identical files. Files that are ninety-something percent the same.

Alan: How does that even work at forty-four billion files? You can't compare every file to every other file.

Ada: You can't, and the trick is the interesting part. Instead of comparing whole files, you reduce each file to a small fixed-size signature — they use two hundred and fifty-six little hash samples per file — and files with similar signatures land in the same bucket. You only compare within a bucket, and then verify the real overlap on the ones that collide. So an impossible all-pairs comparison becomes a cheap one.

Alan: Because public code is unbelievably repetitive. The same boilerplate, the same config, the same tutorial copied into ten thousand repos.

Ada: And if you don't remove it, the model spends its training budget memorizing the thing it's already seen ten thousand times, and it overweights whatever got copied most. So dedup isn't tidiness. It's what stops the corpus from being a popularity contest — and it's a large part of why a hundred and thirteen terabytes collapses to sixteen.

Alan: What else?

Ada: Quality filtering with heuristics — throwing out autogenerated junk, files that are mostly data, that kind of thing. And then the one I think is quietly the important one: personally identifiable information redaction. They run a model called StarPII across the whole corpus and replace emails, secret keys, names, passwords, and network addresses with placeholder tokens.

Alan: Because people commit secrets to public repos constantly. We literally covered a story ten days ago about a coding tool uploading somebody's environment file full of live keys.

Ada: Constantly. And every one of those, left in, is something a model can memorize and later emit. So the redaction pass isn't a nicety — it's the difference between a corpus you can defend shipping and one that leaks its training data on request.

Alan: Okay, let me be the skeptic, because I think there's a real question here. Everything you just described — dedup, license detection, stripping secrets — that's governance. It's hygiene. None of it obviously makes the resulting model better at writing code. So what's the actual payoff?

Ada: That's the right challenge, and I'll concede the front half of it. The dataset card ships no model results. This is infrastructure, not a capability claim. Nobody's saying "train on this and your model jumps ten points."

Alan: So why is it a release worth the airtime?

Ada: Because for the people it's aimed at, provenance is the product. If you're a company fine-tuning a code model, the thing that gets you blocked in legal review isn't your benchmark score. It's not being able to say where your training data came from, whether you were allowed to use it, and whether it's full of other people's secrets. This corpus answers all three by construction — an open, attribution-style license, license detection per file, the personal data stripped, the whole pipeline documented.

Alan: And that's a shift from how the last generation of these got built.

Ada: It's the whole shift. A few years ago the recipe was: scrape everything, train, and sort out the provenance never. What's changed isn't the scraping — it's that the scraping is now a documented, licensed, redacted artifact you can point a lawyer at. The data went from something you hoped nobody asked about to something you can hand over.

Alan: So it's the auditable option.

Ada: It's the auditable option. And that's the through-line of a beat we keep coming back to — the reliability and the governance of a system get decided in the data layer, upstream of the model, where nobody's looking. The lead engineer, Leandro von Werra, framed the release partly around wanting solid open code models for cyber defense. You can't build a defensible model on an indefensible pile of data.

Alan: I'll take that. Two limits I'd flag, though, for anyone reaching for it.

Ada: Please.

Alan: One, it's a snapshot — GitHub as of early August last year. Code data ages, and a year is a long time in, say, a fast-moving framework. Two, the card is explicit that you still have to respect the original repositories' terms. So the license detection helps you, but it doesn't fully absolve you. The compliance work lands back on your desk.

Ada: Both true. And it deliberately leaves out the extras the earlier version bundled — issues, pull requests, documentation, math. This is code and notebooks, on purpose.

Alan: Which is a scoping choice, not a flaw. But know what you're getting.

Ada: Know what you're getting. The pairing with your story is the thing I keep turning over, though. Everyone spent yesterday reading Opus five's benchmark table. This is the layer those tables sit on top of, and it went out the same week to a fraction of the attention.
