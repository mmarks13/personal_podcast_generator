The model already knows what to throw away

Alan: Okay, mine's a paper, and it's the kind I like — it doesn't add anything, it notices that something you were already paying for was there all along.

Ada: Go.

Alan: Coding agents drown in context. You point one at a repository, it reads files, runs tests, reads stack traces, and within a few turns the window is mostly things that mattered eleven steps ago.

Ada: And we've been through why that costs what it costs, so skip the tax.

Alan: Skipping it. The standard fix now is a pruner — something that looks at all that accumulated text and decides which lines to keep before the next turn. The previous version of this, SWE-Pruner, does it by attaching a separate code classifier. A second model, that you also have to run.

Ada: Which is the thing I'd object to immediately. You've added an inference call to save inference calls.

Alan: That's exactly the objection, and the new paper — SWE-Pruner Pro — answers it in a way I found genuinely satisfying. Their claim, and it's the subtitle of the paper: the coder model already knows what to prune.

Ada: Meaning what, mechanically?

Alan: Meaning that when the agent reads all that context in the prefill pass, it computes hidden states for every token anyway. That isn't extra work, that's the work. So instead of a second model reading the same text again, they attach a small head to the frozen backbone that reads the last-layer hidden states and turns them into line-level keep-or-prune decisions.

Ada: Frozen backbone. So the coding model itself is untouched.

Alan: Untouched. The head is a learned length-aware embedding, so the decision is conditioned on how long the response is expected to be, plus a small feed-forward classifier. Trained with a balanced focal loss, to stop it learning the easy answer of keeping everything.

Ada: So the pruning signal is free, in the sense that the computation it reads had already been done.

Alan: Almost free. They report about fifteen percent additional wall time relative to generation. Not zero. But no second model sitting in memory, and no second forward pass over the context.

Ada: Numbers.

Alan: Up to thirty-nine percent fewer tokens on a benchmark called SWE-QA-Pro, running Qwen three coder next — that's an eighty-billion-parameter mixture of experts with about three billion active. And thirty percent on a long-context benchmark called Oolong, with MiMo V-two Flash, three hundred nine billion total and fifteen billion active.

Ada: And the damage?

Alan: That's the part I had to read twice. On MiMo they report the resolve rate on SWE-Bench Verified going up three point eight percent, and Oolong accuracy up two point two points.

Ada: Up. Pruning improved accuracy.

Alan: Up.

Ada: I want to be a little unkind about that, because "we deleted information and it got better" is usually the shape of a bug.

Alan: Be unkind. But there's a boring explanation, and I think you'll like it. Long context isn't only expensive, it's distracting. If turn fourteen still contains the stack trace from a bug you fixed at turn three, that isn't neutral ballast. That's a wrong answer sitting in the window looking authoritative.

Ada: So you're not adding signal, you're removing a distractor. That I accept, and it's consistent with everything we know about models losing things in the middle of a long window.

Alan: Right.

Ada: Here's my real objection, and it's about the headline rather than the method. "The model already knows what to prune." What they've shown is that a small head reading last-layer states can be trained to predict relevance. That means the information is present in the representation.

Alan: Which is not the same as the model using it.

Ada: It is not the same as the model using it. Those are different claims, and the second one is much stronger. The result is still useful — arguably more useful, because it's far easier to exploit a representation than to fix a behaviour.

Alan: Agreed. And I'd add a deployment caveat that matters more than either of us being right. Fifteen percent overhead against thirty-nine percent fewer tokens is a clear win if you're paying per token. If you're latency-bound — if what you care about is time to first useful action — that trade gets much closer, and it might not be a trade at all.
