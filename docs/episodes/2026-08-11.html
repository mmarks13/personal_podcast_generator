Five walls and a live project

Alan: Docker describes five isolation layers: hypervisor, network, Docker engine, workspace, and credential proxy. The important word is layers. A micro virtual machine can protect the host operating system while a read-write mount still gives the agent authority over the project you care about.

Ada: Take the micro virtual machine first.

Alan: Each sandbox has its own Linux kernel. Processes inside are separate from the host and other sandboxes. The agent can have sudo privileges inside that machine because the hypervisor, not a polite in-machine user account, is the primary boundary.

Ada: Which is materially different from putting an agent in an ordinary container that shares the host kernel.

Alan: Yes. Packages, services, and the agent's containers live inside the micro virtual machine. Docker also gives the sandbox its own Docker engine, so a coding agent can build images or run Compose without receiving the host Docker socket.

Ada: Mounting the host socket would let the supposedly contained agent control the host daemon and everything that daemon can reach.

Alan: Docker avoids that path for processes inside the sandbox. But the documentation names an exception: local standard-input M C P servers run on the host. If one of those tools starts a host process or a host container, the micro virtual machine is no longer the relevant boundary for that action.

Ada: A sandboxed agent can hold an unsandboxed tool handle.

Alan: Precisely. The tool's implementation and policy decide what that handle can do.

Ada: Network layer.

Alan: Each sandbox gets an isolated network. Web traffic goes through a host proxy that enforces domain policy. Docker says raw T C P, U D P, and I C M P are blocked, along with private and link-local address ranges. The setup offers three presets. Open allows everything. Balanced denies by default while allowing common development sites. Locked Down blocks everything until you add a rule.

Ada: Balanced sounds safe until common becomes a wildcard broad enough to contain a service you did not intend.

Alan: Docker makes that warning itself. Some default domains are broad. The practical action is to list the active rules, remove what the job does not need, and watch the outbound connection log. A default-deny label is a starting configuration, not evidence that the allow list is minimal.

Ada: Credentials cross that proxy too.

Alan: For supported services, the real secret stays on the host. The sandbox sees a sentinel value. When an allowed request matches the declared service, the host proxy inserts the actual authentication header on the way out.

Ada: That prevents the agent from printing the raw key. It does not prevent the agent from spending the key's authority through an allowed request.

Alan: Exactly. Secret confidentiality and service authorization are different. A model token can remain unreadable while the agent still calls the model. A GitHub token can remain unreadable while an allowed tool uses it to open a pull request. Scope the account and service permissions as though the agent can exercise them, because it can.

Ada: Then comes the workspace, where the product's reassuring name meets the user's files.

Alan: Direct mode is the default. Docker mounts the selected working tree read-write, and changes appear on the host immediately. The documentation says there is no isolation between the agent and that workspace in direct mode.

Ada: Not merely source files.

Alan: Correct. The agent can alter build scripts, continuous-integration configuration, editor tasks, project-level A I instructions, hidden executables, and Git hooks. Docker points out that Git-hook changes do not appear in an ordinary Git diff. Deleting the micro virtual machine does not reverse edits already written into the host working tree.

Ada: That is the sentence I want people to retain. Disposable environment does not mean reversible project.

Alan: Clone mode changes that. The host repository enters read-only, while the agent works on a private clone inside the micro virtual machine. Changes stay there until you deliberately fetch them or the agent pushes them somewhere its network and credentials permit.

Ada: And deleting the sandbox deletes that private clone, so isolation adds a recovery obligation in the other direction.

Alan: Fetch or push work you want to keep before removal. A good boundary can protect you from unwanted writes and still eat wanted writes if you forget where they live.

Ada: You have named four layers. What makes the fifth more than credential injection?

Alan: Docker treats credentials as their own isolation layer because the sandbox can use services without possessing raw secrets. But I would add two narrow crossings that are easy to overlook. Shared agent skills can be mounted read-write from one host-side store into multiple sandboxes. One sandbox can change instructions another later consumes. And the M C P gateway brokers tools that may run outside the virtual machine.

Ada: So two sandboxes that share skills are not independent at the instruction layer, even if their kernels cannot talk.

Alan: Right. Docker calls that a trust-boundary exception. You can opt out of shared skills for a sensitive run. You should also inventory every M C P server and ask where it executes, not merely whether the calling agent is sandboxed.

Ada: Give me your launch checklist without turning this into a configuration manual.

Alan: For an untrusted coding task: use clone mode. Start with Locked Down networking and add only the model provider, package registries, and repository host the task requires. Use a narrowly scoped account. Opt out of shared skills unless you need them. Permit no host-side tool you have not reviewed. Preserve the commits before deletion. Then inspect both the Git changes and the network log.

Ada: Docker says the command-line sandbox is free, including commercial use. Centralized organization governance is the paid part.

Alan: Which matters because a local policy chosen by one careful developer is not an organizational control. A company needs the same network, filesystem, credential, and M C P rules applied across every machine, plus evidence that they stayed applied.

Ada: Does this make unattended agent execution safe?

Alan: It makes one answer much better. The agent should not own the host merely because it needed to run a build. It does not make the shared repository harmless, the allowed destinations trustworthy, the tool servers contained, or the service permissions appropriate.

Ada: Then Docker has built a real security product, and the honest product description is longer than sandbox.

Alan: Much longer. My test is simple: name the asset you are protecting. Host operating system? Working tree? credentials? remote account? downstream deployment? Then point to the layer that protects that asset and the path that still crosses it.

Ada: The Texas letter is also a list of boundaries, except the disputed asset is public infrastructure and the question is who carries the cost.
