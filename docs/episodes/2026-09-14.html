The paper that stops running the experiment

Ada: Go.

Alan: You want an agent that does empirical research — reads a task, writes the code, runs it, sees whether the number went up, learns from that. To train it with reinforcement learning you need thousands and thousands of those loops. And their observation is that the generation part scales beautifully, because you can batch it on a GPU, while the execution part doesn't scale at all. Every rollout needs a real machine actually running real code for real minutes.

Ada: So the model is cheap and the laboratory is expensive.

Alan: The laboratory is the entire cost. So their move — it's called World Model RL — is to replace the execution with a learned world model that predicts the reward you would have gotten.

Ada: You stop running the experiment and ask a model what would have happened.

Alan: You stop running the experiment and ask a model what would have happened.

Ada: Alan, that's a reward model.

Alan: It is a reward model, and I want to get to your objection, but let me finish the mechanism first because they clearly saw it coming. They add two corrections. The first is online debiasing — the predictor is systematically off in some direction, so you estimate that offset while training and subtract it. The second is inverse-variance denoising, which is the sensible thing: when the predictor is confident, weight its answer more; when it's all over the place, weight it less. ToolGrad: writing the question after the answer

Ada: Different scale entirely, and it's a small, pretty idea. Google Research posted it Thursday — it's an ACL paper from Zhongyi Zhou and Ruofei Zhang at Google XR — and it's about a problem nobody outside the field thinks about, which is where tool-use training data comes from.

Alan: Painfully.

Ada: Painfully, and expensively. The standard way: take a library of APIs, write a plausible user question, then search for a chain of calls that actually answers it. And that search fails constantly, because most chains you try don't execute, or don't produce what the question asked for. You burn enormous compute generating candidates and throwing them away.

Alan: And the surviving data is biased toward whatever the search happened to find.

Ada: Right. ToolGrad's move is to run it backwards. Their line is that it first generates a ground-truth tool-use chain and then annotates its corresponding user prompt. Build a workflow that definitely works, and then write the question it's the answer to.

Alan: Huh. Okay, that's cheating in the good way. You can't fail to find a solution if you started from one.

Ada: You cannot. And the loop that builds the workflow is where the name comes from. Four parts. A proposer narrows the whole API library down to a handful of candidates that could extend the workflow you have so far. Executors actually call them, in parallel, and each one produces an execution report. A selector reads the reports and picks the best one. And then an updater rewrites the synthetic user query and the answer so they match the workflow you now have.

Alan: And the "gradient" is the execution report.

Ada: The gradient is the execution report. That's the borrowed idea — it comes from a line of work on optimising prompts with textual feedback. In ordinary training the signal telling you which way to step is a number. Here the signal is prose: this call returned an error, this one returned the field you needed. You're hill-climbing, and the step is written in English.

Alan: I like it more than I expected to. Give me the numbers, because the numbers are where these things usually fall apart.

Ada: The dataset is called ToolGrad-five hundred, built on ToolBench's library of more than sixteen thousand real-world APIs. Five hundred samples.

Alan: Five hundred? That's not a dataset, that's a weekend.

Ada: That's the striking part. They fine-tuned Gemma three at one, four and twelve billion parameters on it, and on the Berkeley Function Calling Leaderboard the twelve-billion model scores eighty-three point one. For comparison, they list Gemini two point five Pro at eighty-three point two, Claude Opus four point five at eighty-two point eight, and GPT-five at seventy-four point four. They also report their generation pipeline hitting a ninety-nine point eight percent pass rate with fewer optimisation steps than the depth-first search approach it's compared against.

Alan: So a twelve-billion-parameter model matching frontier models on function calling, off five hundred examples.

Ada: On that leaderboard, yes.

Alan: Two things, and only one of them is a complaint. The complaint is that the models it's matching are last year's — Gemini two point five, Opus four point five, GPT-five are not what anybody is calling today. Matching them in September twenty twenty-six is a good result and not the result the number sounds like.

Ada: Agreed. And the other thing?

Alan: The other thing is that this is the right kind of small. Five hundred verified samples beating the pants off a much bigger pile of scraped ones is the single most repeatable lesson of the last two years, and it keeps surprising people.

Ada: There's a real limit though, and it's structural rather than a flaw in their execution. Every sample in that dataset is a workflow the proposer proposed and the executors could actually run. So the data has the shape of the sampler. The questions are reverse-engineered from things that work, which means you never get the query a user actually types — the ambiguous one, the one that wants something the API can't do.

Alan: So it teaches the model to be fluent in successful tool use and says nothing about failure.
