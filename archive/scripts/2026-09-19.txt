## A language that makes you prove it before it compiles
A: Alan sent me a link at eleven at night with no message attached, which is how he asks me to look at something.
B: [laughs] It works.
A: It does. Bend. It went up on Hacker News yesterday, five hundred and ninety-one points, three hundred comments, and the tagline on the site is: a fast language that blocks AI mistakes via proof. The subtitle is four things stapled together — C speed, CUDA parallelism, Lean proofs, Python syntax.
B: Which is four different research programmes and a marketing department.
A: It is. Let me do the idea, and then you can be unpleasant about it. The mechanism has a name and a filename. You write a file called LAWS dot bend, and in it you state invariants about your program. Their examples: the sum of all balances must be zero. Winning is impossible.
B: Invariants. Fine, people write those as tests.
A: Not as tests. As theorems. Bend's type system is an affine dependent type theory, which means the type checker is also a proof checker — the same family as Lean and Rocq, which are the systems mathematicians use to machine-check proofs. So when your code changes, the compiler demands a proof that the laws still hold. Their sentence: merging a bug is mathematically impossible — it is a theorem.
B: And the AI part is just that the thing writing the code is a model.
A: That's exactly the AI part, and I think it's the right small idea. The site's example is an agent producing a bug, the compiler refusing it, and the agent retrying until it produces something that proves out. The claim is: no AI can ship one line that breaks them, ever.
B: [skeptical] Okay. I've got three.
A: Go.
B: One. Writing the law is writing a specification, and the specification is where the bugs are. "The sum of all balances must be zero" is a lovely invariant for a ledger and it does not tell you whether you charged the right account. I can satisfy every law in the file and ship something catastrophically wrong.
A: That's correct and I don't think they'd argue. What it buys you is a small set of things that are now impossible instead of unlikely. That's not nothing — that's the difference between a class of bug and an instance of one.
B: Two. Somebody has to write the proofs. In practice, in a dependent type system, proof effort is not proportional to code size, it's proportional to how awkward your invariant is to state. Easy law, easy proof. Real law about a real system, and you're a graduate student for a fortnight.
A: Their answer to that is partly speed — they claim Bend type-checks in a second at most, against minutes for comparable proof checkers.
B: [pause] Alright, that's more interesting than it sounds, and I'll say why. The reason people bounce off Lean isn't that proofs are hard in principle, it's the loop. If checking takes four minutes you stop exploring. A one-second loop is a different activity. And it's a much better fit for an agent, which will happily try two hundred things.
A: The agent doesn't get bored.
B: The agent doesn't get bored, and this is the first argument I've heard for proof assistants where the agent's tirelessness is aimed at the part that's actually tedious. Usually we point it at the part that was already fun.
A: And the third?
B: Third is the GPU thing, and it's where I get suspicious. The parallelism story is divide and conquer — split the work in two and the runtime spreads the calls across every core it can find, no threads, no locks. Their demo is computing two to the twentieth across four thousand and ninety-six GPU cores. They claim single-core speed near C, and up to a hundred times faster than one core when it spreads.
A: You don't believe it?
B: I believe the demo. Two to the twentieth by recursive doubling is the friendliest possible workload for that model — perfectly balanced tree, no data dependencies, no memory contention. Show me a parser. Show me something with a pointer in it.
A: Which is the standard objection to the whole automatic-parallelism lineage, and it's been a correct objection for about forty years.
B: It has. And I'd separate the two halves of this project cleanly. The proof half I want. The GPU half I'd treat as a research claim.
A: Status, so nobody goes and bets a quarter on it. The repository's own words, capitals theirs: Bend is young, expect bugs and report them. Twenty-one thousand six hundred stars, and this is version two — Bend one and its runtime don't carry over, so the star count is measuring an earlier thing as well.
B: [dry] Good. Say that part loudly. Here's where I land. I'm not going to write my next service in it. But the shape of the idea is right, and it's the first concrete answer I've seen to a question I've been asking badly all year — which is what review even means when the code arrives faster than you can read it. The answer here isn't a better reviewer. It's moving the thing you check from the code to a statement about the code.
