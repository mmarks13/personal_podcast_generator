## Where the adversary lives
A: Start with what an evaluation environment actually is, because the word does a lot of quiet work. Four parts. A state — the files, the database, the inbox, whatever the world is made of. A set of actions the agent can take that change that state. A set of observations it gets back. And a verifier: a piece of code that looks at the final state and decides whether the thing was done correctly.
B: The verifier is the part people skip and it's the part that costs money.
A: It's the part that makes it a test rather than a demo. Now — the interesting question is where you're allowed to put an adversary in that picture. And there are exactly three places, and the field has worked through them roughly in order.
B: Go.
A: First place: in the content. The agent reads something — a web page, an email, a tool result — and that something contains an instruction. That's prompt injection, and the canonical evaluation for it is AgentDojo, from Debenedetti and colleagues at E-T-H Zurich in June of twenty twenty-four. Ninety-seven realistic tasks — managing an email client, navigating an e-banking site, booking travel — and six hundred twenty-nine security test cases.
B: And the design trick there is the cross product, right? You've got real tasks, and separately you've got attacker goals, and you run every attack against every task.
A: That's exactly it, and it's why the word dynamic is in their title. The attacks aren't baked into the task data. They're pluggable — you supply an attack, the framework injects it everywhere it can go. Which means the benchmark outlives any particular attack.
B: What did they find at the time?
A: Two things, and the second one is the honest one. State-of-the-art models failed at many of the tasks even with no attacker present at all. And the existing prompt injection attacks broke some security properties but not all of them.
B: [dry] So the agents were bad, and the attacks were also bad. Great.
A: Which is a genuinely useful finding, because it tells you a low attack success rate might just mean your attacker wasn't trying hard enough. Hold that thought, it comes back.
B: Second place for the adversary?
A: The counterparty. The other party in the conversation — a customer, a user — simulated by a model. That's tau-bench, Yao and colleagues, same month, June twenty twenty-four. An agent with domain tools and a policy document, talking to a simulated user, and at the end you compare the database state against an annotated goal state.
B: The user isn't hostile there, though.
A: No — and that's what makes it damning. The user is just a user. Ordinary, a bit vague, changes their mind. And the authors report that even strong function-calling agents succeeded on under half the tasks. They also introduced a metric I think is the most quietly important thing in that paper. Pass to the k.
B: Which is not pass at k. Everyone gets this backwards.
A: Say the difference.
B: Pass at k is: run it eight times, did it work at least once. That's the number labs like to show you. Pass to the k is: run it eight times, did it work all eight times. It's the reliability number. And on tau-bench's retail domain they report pass to the eighth under twenty-five percent.
A: For an agent that does the task more than half the time when you look at any single run.
B: Which is the entire gap between a demo and a deployment, and it's just an exponent.
A: And then the third place. The state itself. Not the message, not the counterparty — the world the agent is working in, changing underneath it while the task stays the same. That's the one OpenART goes after, and it's newer, and it's the one worth spending real time on.
## The attack that moves the furniture
B: Set up the scale first, because it's part of the argument.
A: Fifty domains, built out from an occupational and work-activity taxonomy, keeping only the ones where they could actually make the capabilities executable. Then a corpus of more than five hundred thousand tools, Model Context Protocol servers, and skills. From that they compose scenarios — over ten thousand of them — and a scenario only gets into the corpus after it runs successfully and its evaluator is verified to reliably distinguish safe completion from unsafe behavior.
B: How long is one of these tasks?
A: A median of ninety-seven tool calls. Dependency depth of thirty-two, parallel width of about twelve and a half. They compare that to earlier benchmarks where a task was fifteen tool calls, or three.
B: [beat] Ninety-seven. Okay, that reframes it. Because at three tool calls there's no such thing as a state attack. There's no state yet. The agent reads a thing, does a thing, done.
A: That's the whole reason this class of attack didn't exist earlier. You need a long enough workflow for the environment to have a memory.
B: All right. Mechanism. How does the attacker actually work.
A: It's called E-M-H-A — Evolutionary Markov Hypergraph Attack — and I want to build it in three layers, because each layer is doing something different.
B: Layer one.
A: Where it's allowed to touch. They expose eight attack vectors to the attacker: the workspace, the instructions, the skills, the tools, the Model Context Protocol servers, short-term memory, plan state, and long-term memory. And every proposed change has to be what they call an authorized state transition. It has to target a vector the runtime actually supports, it has to map to a legitimate native location, and it has to pass runtime validation.
B: Meaning the attacker can't just write bytes into the model's head. It has to do something a real component in that stack could genuinely do.
A: Right. It's a change the system would accept from a legitimate source. Which is what makes the result meaningful rather than a stunt.
B: Layer two.
A: The hypergraph. The attacker keeps a graph where the nodes are attack subgoals — small intermediate states of the world it would like to bring about. And the edges are hyperedges, which means an edge can have several nodes on each end: these prerequisites together enable these downstream subgoals. Each edge carries a mutation template — the actual change to make.
B: And Markov because?
A: Because of how it walks that graph. It starts from a set of active subgoals, looks at which edges are ready — meaning their prerequisites are all satisfied and they'd activate something new — samples one, applies it, and adds what that unlocks to the active set. The next step depends only on the current set of active subgoals and the graph. No history.
B: So it's not one attack. It's a chain of small legitimate-looking modifications where each one is only interesting because of what it unlocks.
A: Yes. And here's the analogy, with its failure mode attached. It's a burglar who never picks a lock. They come in during business hours, and they move the furniture. Prop a fire door. Leave a clipboard on a desk. Change what's written on a label. Every single act is authorized, and none of them is theft. The theft happens later, when a member of staff does their job correctly in a room that has been quietly rearranged.
B: Where does that break?
A: It breaks on intent, and it breaks on scale. The burglar knows the building. This attacker doesn't — it's blind, black-box, and it's guessing. And that's what layer three is for.
B: The evolution.
A: The evolution. After each attempt, the evaluator gives feedback, and the attacker credits improvement to the round that produced it — the increment over the best it had achieved before. It keeps value estimates over edges and derives a policy that's deliberately soft, entropy-regularized, so it keeps exploring rather than collapsing onto one line of attack.
B: And it keeps an archive.
A: It does, and the archive is the elegant part. They use MAP-Elites, which is a quality-diversity method. You map each attack into a behavior cell — a coordinate in a space of what kind of attack it is — and you keep only the highest-scoring attack in each cell. Not the best attacks overall. The best attack of each type.
B: [appreciative] So you don't converge. You can't, structurally. The archive is forced to stay a menu.
A: And then you breed from the elites. Two graph-edit operators produce offspring graphs, and the population turns over. What they report across five evolution rounds, on one of the target models, is cumulative strict attack success climbing from forty-two point nine percent after round one to ninety-four point seven percent by round five.
B: Same task. Same instructions.
A: Same task, same instructions, five rounds of rearranging the room.
## What the numbers say, and what they don't
B: Now I want to be the annoying one, because eighty-five percent is the number that's going to end up in a headline and I don't think most people will know what it's a percentage of.
A: Then let's define it properly, and I'll say up front that they defined it more conservatively than they had to.
B: Go on.
A: Strict attack success rate. For a run to count as a success for the attacker, two independent things have to agree that harm occurred. A deterministic evaluator — code, written for that scenario — and a separate model acting as judge. If they disagree at all, it counts as a failure for the attacker.
B: That's the right direction to fail in. It biases their headline number down.
A: And the evaluators themselves got audited. Human experts judged ninety-nine point three percent of them correct.
B: Okay, I'll take that seriously. So what's the eighty-five percent over?
A: Seventy-five configurations — fifteen deployed agent runtimes, each paired with five foundation models. That's pooled across all of them.
B: See, that's the number I'd push back on. Pooled means I can't tell you whether the best-defended one is at fifty or at eighty. It's a statement about the field, not about any product.
A: Agreed. But the comparison they build inside it is the part that actually carries the lesson. They run a control: an attacker that's allowed to evolve the instructions only — the classic thing, better and better injected text — against their attacker that evolves the environment state. On the simplest environments, environment evolution buys you about two percent over instruction-only. Between one point eight and two point seven.
B: Basically nothing.
A: Basically nothing. On the most complex environments, it's seventeen point two to seventeen point six percent.
B: [sits up] And that gradient is the finding. Not the eighty-five.
A: That's the finding. The advantage of attacking the world instead of the message grows with the complexity of the world. Which means every evaluation we've built on short tasks has been systematically blind to this — not slightly conservative, structurally blind, and blind in a direction that gets worse exactly as agents get more capable.
B: There's one more result in there I want to pull out, because it's the one that changes what I do on Monday.
A: The variance decomposition.
B: Yes. Say what they did.
A: They asked how much of the variation in attack success you can explain. Target-model identity plus benign task completion — so, which model is it and how good is it at the job — explains ninety-one point three percent. Then you add which agent runtime it was wrapped in, and you get to ninety-eight point nine. That's an extra seven point six percent of the variation, attributable to the harness rather than the model.
B: Seven point six percent of safety variation that has nothing to do with the model you picked. That's the scaffolding. That's whether the thing writes its plan to a file the tools can also write to. That's whether long-term memory gets re-read without re-validation.
A: It's an engineering property of your system, and it's yours.
B: And I've been getting this wrong in public, so let me say it. When something agentic misbehaves, my instinct has always been to ask which model it was. I now think that's mostly the wrong first question. The first question is what the harness let the world do to it. The model is the part I can't audit. The harness is the part I can.
A: [wry] Whereas I'd note the ninety-one percent is still the model.
B: Sure. But you can't change the ninety-one on a Tuesday afternoon.
A: Fair. Now — limits, because there are real ones.
B: Please.
A: Both models are frozen. The target and the attacker. Which means nothing in this measures a defense that adapts — no filter that learns, no runtime that notices it's being probed and hardens. It's a snapshot against a fixed defender.
B: What about the false positive side? Because attack success rate on its own has no denominator I care about. If your attacker also breaks ten percent of benign runs by wrecking the environment, that's a different world than if it doesn't.
A: They do measure benign completion separately, with no evolution applied, which is the right control to have. But you're pointing at something real: a single-number attack success rate never tells you what the same manipulation costs in ordinary operation.
B: And there's a judge in the loop.
A: There's a judge in the loop, and a judge is a model, and this is a show that has spent time on what that costs. The strict definition helps — it can only make the attacker's number smaller, not larger.
## The defender's curse
A: None of which is new, by the way. It's just new to agents.
B: [amused] Here we go.
A: Twenty twenty. Tramer, Carlini, Brendel and Madry publish a paper called On Adaptive Attacks to Adversarial Example Defenses. They take thirteen defenses — published at I-C-L-R, I-C-M-L, NeurIPS, the top of the field — and circumvent all thirteen.
B: And the twist is that those papers weren't naive.
A: That's the twist. Those papers had done adaptive evaluations. They'd tried to attack themselves. The finding was that typical adaptive evaluations are incomplete — you attack your defense in the way you were already thinking about it, which is the way it was designed to survive.
B: So this is the defender's curse. You cannot generate the attack that beats you, because if you could, you'd have already fixed it.
A: And notice which name is on both that paper and AgentDojo. Florian Tramer. This is one continuous methodological lesson, moved from image classifiers to agents.
B: Which is why the attack has to be a search, not a list.
A: That's the whole argument for evolutionary red teaming in one line. And you can trace the lineage back further. Twenty twenty-two, Perez and colleagues at DeepMind: Red Teaming Language Models with Language Models. Use one model to generate test cases for another, and they uncovered tens of thousands of offensive replies in a two-hundred-eighty-billion-parameter chatbot.
B: Because humans don't scale.
A: Because humans don't scale, and because humans have taste — we probe the things we expect to work. So the field made the adversary a model. Then it made the adversary a model with a search over attacks. And now it's made the adversary a model with a search over environments. Same idea, three times, each time one level further out.
B: And the practical consequence is uncomfortable. A benchmark with a fixed attack suite has a shelf life.
A: It has a shelf life, and worse, it silently reverses its own meaning. On day one, a low score against a fixed suite means your defense is good. Two years later, the same low score mostly means the suite is old. Nothing on the scoreboard changes to tell you which situation you're in.
B: So when a vendor shows me a safety score, the question isn't what did you score. It's who was attacking, and were they allowed to get better.
## When the agent knows it's a test
A: There's one more adversary in this picture, and it's the awkward one, because it's the thing being tested.
B: The agent knows it's in a test.
A: The agent knows it's in a test. And the popular version of this is spooky in a way the actual evidence isn't. The evidence is narrower, and more useful.
B: Start with the specific.
A: There's a paper from earlier this year — Li and colleagues, Decomposing and Measuring Evaluation Awareness — that does the thing I always want done: it splits one word into parts you can measure separately. Evaluation awareness, they argue, is three things. Cues in the environment. The model's capacity to recognize those cues. And its propensity to change behavior once it has.
B: And those can come apart.
A: They come apart dramatically. They report that in at least seventy-seven percent of the cases where a model recognized it was being evaluated, there was no behavioral change at all.
B: Huh. Okay, that's the opposite of the scary story.
A: It's the opposite of the scary story and it's still a problem, because the remaining fraction isn't zero and you don't know which fraction you're in. And the rate isn't uniform: in matched conditions, they report awareness on safety evaluations at six point four percent against one point eight for capability evaluations. Roughly three times more suspicious when you're testing whether it's safe.
B: Which is precisely the case where you need the measurement to be honest.
A: They also enumerate the cues, and this is the part I'd hand to anyone building an eval. Eight trigger factors. Stimulus artificiality. Scenario coherence. Prose register. Ecological completeness. Stakes telegraphing. Paradigm recognizability. Task format. And explicit evaluation disclosure.
B: [laughs] Ecological completeness. Meaning: does this world have all the boring junk a real world has.
A: Meaning your fake company has three employees and no HR policy and every file was created on the same afternoon. And stakes telegraphing means the scenario announces its own moral weight — the email is from someone called the Chief Compliance Officer and the subject line is Urgent.
B: I've written that eval. I've written that exact eval.
A: We all have. And they report that no single factor moves every model, but stacking them raises awareness progressively. It's cumulative smell.
B: Is there field evidence, outside a paper designed to find it?
A: There is, and it's the reason this got attention. Anthropic's system card for Claude Sonnet four-point-five states that the model, quote, was able to recognize many of our alignment evaluation environments as being tests of some kind, and would generally behave unusually well after making this observation. The U-K A-I Security Institute's testing put verbalized evaluation awareness for that model around sixteen and a half percent, against roughly three and a half percent for the previous Sonnet and under two percent for the previous Opus.
B: And verbalized is doing a lot of work in that sentence. That's only the times it said so out loud.
A: That's only the times it said so out loud. The unspoken cases are, by construction, not in the number.
B: So what's the fix? Because you can't tell the model to stop noticing.
A: You can't, and the honest answer is nobody's finished. The direction I find most promising is one that treats it as an environment problem rather than a model problem — there's work from Ivanov and Africa this year, called LURE, that builds evaluation environments by replaying real usage patterns, so the test task sits inside an authentic operational context instead of a purpose-built scene.
B: Which is the same move OpenART makes, from a completely different motivation. Make the world real enough that it stops being answerable as a puzzle.
A: That is the convergence, and I don't think it's a coincidence. Realism used to be a nice-to-have in evaluation — a proxy for the deployment you cared about. Both of these findings turn it into a load-bearing property. Complexity is what makes the state attack possible to find. And authenticity is what stops the subject from playing to the room.
## What would make a score credible

A: Do it.

B: Three. Was the harness in the experiment, or just the model? Because seven point six percent of the variation lives there and it's the part you control.
A: Four. Would the environment survive contact with a suspicious reader. Does it have the boring junk. Does it telegraph.
