## How Claude Code checks its own work
B: Switching to something I can actually run. Addy Osmani's post opens with the claim the whole thing hangs on. Quote, "Without them, you can really only run one or two Claudes at a time, because you have to check everything yourself. With them, you can run dozens or hundreds in parallel." "Them" being verification loops.
A: So the bottleneck is you.
B: The bottleneck is always you. And they say plainly that on the Claude Code team, about ninety percent of the code is written and reviewed by Claude. So reading every diff isn't an option. The post is about what replaces it.
A: Go through it.
B: Three kinds of test, and they rank them. If you pick one, they say pick end-to-end. A test that walks a real user flow. Add an item to a cart, check out, land on the confirmation page. Their line is that end-to-end tests are "difficult to fool–either the whole feature works or it doesn't."
A: As opposed to unit tests.
B: Which are faster and less flaky, and here's the agent-specific bit. You can pass them and still break the feature, quote, "because both the agent and the test don't understand the full task." The agent writes the code and the test from the same misunderstanding, and they agree with each other perfectly.
A: Two witnesses who rehearsed together.
B: [laughs] Exactly. So they give the agent hands and eyes on the running app. The Chrome extension for web work, phone tooling for mobile, computer use for desktop. And they package that as a skill called verify that Claude runs before it commits. They call it their smoke test harness, and say, quote, "you want it rock solid."
A: Second kind?
B: Property tests. You write down something that can't be false, and a library throws thousands of generated inputs at it trying to break it. Encode then decode, you get back what you started with. A balance never goes negative. Do a migration twice and it's the same as once. Optimized code gives the same answer as the slow, obviously correct version.
A: That's an old idea, and it's nice to see it back. Koen Claessen and John Hughes published QuickCheck in two thousand, a little Haskell library that took properties as functions and tested them on random inputs. The whole point was that the machine picks the cases, not you.
B: And that's the post's argument for agents. Property libraries generate edge cases "that aren't created with the same bias as the agent that created the original code." The agent's blind spots don't get to pick the test inputs.
A: And the third?
B: Differential tests. For migrations. Run the old system and the new one on the same inputs, random or sampled from production traffic, and any difference is a bug or a breaking change. Their heading is "the old system is the oracle." You normalize the noise, whitespace, and keep a list of differences you meant to make.
A: Okay. Here's where I push. Ninety percent written by Claude, and also reviewed by Claude. Then Claude runs the checks. Where's the person?
B: Two places, and they're specific. One: failures decide what a person sees. Claude runs the checks and tries to fix what fails. If a check still fails after three rounds, it stops and brings in a human. Two: the people who own the code write its checks, and tune them until they flag what the owner would flag.
A: So the human moves from reading the change to writing the thing that reads the change.
B: Which is their last line, almost word for word. Your job shifts "from reading every diff to defining what 'done' looks like and reviewing the evidence."
A: I'll take a little credit there. Back in October I said the most valuable thing in an agent's pull request is a statement of what you meant, written before the code. They've turned that statement into something that runs. I like that better than my version.
B: Noted for the record. And there's a rule I think you'll like even more. Quote, "If a change can modify the check that judges it, the check is broken." Their review tool reads its instructions from the main branch, never from the pull request. A passing review on an old commit "means nothing."
A: We've said before that a visible test becomes a target. This is the narrower, enforceable version. The agent can see the check. It just can't edit it.
B: And they're honest about the gaming. Flaky tests train the agent to rerun instead of fixing, so Claude can't skip a flaky test, add a sleep, or retry until it passes. If it can't find the cause, it deletes the test and writes down why.
A: Deletes it. You're comfortable with that?
B: With "writes down why," yes. A flaky test that everyone ignores is worse than no test, because it teaches you to ignore red. They also stamp every commit with how it was verified, and the stamp can say "none," so you can go find the unverified ones.
A: My last worry. This is a team building the tool, describing the tool, with every incentive to make it look easy. Where's the number that says it works?
B: Thin. There's one, from internal testing, that a separate grader checking against a rubric improved task success "by up to 10 points," with no units on the page. Mostly it's a process. And notice one thing they tell you not to do. Don't stack a second, pricier reviewer on top. Tune the one you have.
A: So no proof, just a way of working.
B: A way of working I can copy this afternoon. A verify skill, one end-to-end test, and a rule that the change can't touch its own judge. If I'm wrong about it, the commit stamps will tell me.
