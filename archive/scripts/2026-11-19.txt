## The review bottleneck, revised
A: The Harvard paper. Fiona Chen and James Stratton, both Ph.D. candidates. We went through the core finding last month: coding tools pour out more code, and review becomes the constraint. The new version, dated November fourteenth, changes two things. It splits the effect of coding agents from the older autocomplete-style assistants. And it adds a model that forecasts out to twenty thirty-one.
B: Same data?
A: Same partner, a longer window, now through August. Jellyfish, an engineering analytics platform. Six hundred fifty-five firms, about seven hundred twenty thousand workers, four hundred forty-five million work events: commits, pull requests, tickets, calendar entries. Twelve months after a firm adopts agents, the authors report lines of code up forty-four percent, commits up thirty-six, pull requests opened up about thirty-six.
B: Lines of code is a terrible metric.
A: They know, and they check whether it's just verbose A-I code. Here's the number I find most telling, and it's new. With assistants, almost all the extra pull requests get merged, close to the baseline rate. With agents, only about sixty-three percent of the extra pull requests get merged, against eighty-six percent at baseline.
B: So a third of the extra agent work just dies in review.
A: Or gets abandoned on the way there. And the work that ships barely moves. Completed tickets rise about fourteen percent with agents, which they call marginally insignificant. They can rule out anything above about thirty-one percent.
B: And the review side?
A: Time from submitting code for review to approval goes up fifty-six percent. They split that into time waiting in the queue, up about sixty percent, and time in active review, up about fifty-nine. Comments per change up almost thirty-nine percent. And seventy-nine percent of firms have adopted A-I code review tools, but humans still write the overwhelming majority of reviews.
B: So the queue is longer and each review is slower. That second part is the one that'd worry me. A longer queue is a staffing problem. Slower reviews mean the code is harder to read.
A: Their model puts numbers on exactly that. Agents raise coding productivity about seventy-four percent and slightly lower review productivity, minus seven. Firms respond by moving people, coding labor down about twenty-three percent, review labor up about forty-three. And there's one quote from their interviews I keep thinking about after the last segment. An engineer describes a project where one senior engineer was the only one allowed to approve changes, and could review their code once a week. Then, quote, "after some outages that were caused by AI-generated commits, there were also new rules requiring senior engineer approval for AI-generated code."
B: Outages make more review. Review makes the queue. That's a loop.
A: And it's why the forecast is the part people are arguing about. They run two scenarios. If review productivity stays where it is, output rises about fifty-eight percent by twenty thirty-one, levels off by late twenty twenty-seven, and employment falls about ten percent. If A-I makes review as productive as it makes coding, output rises about three hundred forty percent and employment falls seventy-six percent.
B: Seventy-six. That's the number that's going to travel.
A: And they say it shouldn't, on its own. They call that scenario an upper bound, one where A-I does essentially all of software engineering, because their model only has two inputs, coding and review. Real software has planning, scoping, everything else.

A: All true, and the paper says Jellyfish reviewed it only for proprietary information, not content. But here's what's changed in how I read it. The slow, human, senior part is where the jobs are.
